The content layer

Tokenized markup, not opaque binary

The genuinely load-bearing discovery: past the header, .nxt is mostly literal HTML text with a thin, mostly-decoded opcode layer spliced in. That's what makes decoding straight to HTML possible at all.

The most common token: a length-prefixed run of literal markup or text. Subtype 0x37 is a tag, 0x39 an HTML entity. A high bit on the length byte signals an extended 2-byte length for runs over 255 bytes.

Document boundaries & paging

Where it still breaks: mid-token interruptions

The single biggest open problem. A recurring binary marker — built around the literal string LPDD — can appear inside a literal-text token, not just between documents, and swallow whatever it interrupts.

normal token
<!DOCTYPE html PUBLIC …>
<title>F.S. 7.08</title>
F.S. 7.08, actual bytes
<!DOCTYPE html PUBLIC "-//W3…
6-byte marker
unrelated body text resumes — the rest of this token is gone

Confirmed example: a 239-byte <!DOCTYPE…> token gets cut off after ~29 bytes by a second, unrecognized marker, and decoding resumes mid-sentence inside a different document entirely. Section bodies are usually intact on both sides — but not always: § 145.11 is a confirmed real section (present in the live table of contents) that both the title scan and the SectionNumber recovery path failed to find at all. It's simply missing from the index today.

LPDD ≈ 4KB storage page, not one document marker can be 5–50+ bytes, shape varies no real paging/record model built yet

The unknowns

What we genuinely don't know

Not "haven't gotten to yet" — these are places where testing hypotheses against real content hasn't produced a confident answer.

What does \x15 encode?

Seen near special characters (an EM SPACE once followed it) but never decoded field-by-field.

What triggers a mid-token interruption?

No model exists for when a page marker splices into a literal run versus sitting cleanly between documents.

How many "double failure" sections exist?

§145.11 proves the pattern exists. Nothing yet can scan the full index and count how often it happens.

What are the two checksum-shaped fields?

Bytes 0x11E–0x11F and 0x1AE–0x1AF vary per file with no obvious correlation to anything else we've checked.

What's the 8-byte ID at 0x100?

Unique per file, doesn't match any other observable property. Hash? GUID? Timestamp? Unclear.

What's inside data1.cab / data2.cab?

Unextracted InstallShield cabinets. Likely contain the real Folio/NXT rendering engine (nfoenu6.dll is referenced by name inside fs2025.nxt but isn't present as a file in this download).

What do the other 11 files hold?

Only fs2025.nxt is decoded and indexed. xrt2025.nxt is confirmed as a catchline keyword index; the rest (constitution, connection index, name index, tables) are filename-based guesses only.

Is there a real offset index anywhere?

Linear scanning is fast enough (0.7s for the whole 240MB file) that no one has needed to look for a binary lookup table — so it's untested, not ruled out.

Resolved, for the record

The bundled installer executables (Work-Set.exe, Serv-Go.exe, Serv-Out.exe, and their DLLs) are confirmed WinBatch-compiled install/service helpers, not the Infobase engine — a dead end, closed.
